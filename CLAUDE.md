# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Krini Weather Station is a Raspberry Pi 4 weather station in Kalamaria, Thessaloniki. It serves a public Dash dashboard at weather-krini.ngrok.io (ngrok → port 8050). The station uses sensors attached to the Pi (wind, PMSA003I air quality, AS3935 lightning, SEN0575 tipping-bucket rain, zenith sky camera) and remote ESP32 boards (BME280, MCP9808, UV, light, LM393 rain). All code is Python plus a few bash loop wrappers. There is no build, lint, or test suite. To check a change, run the script directly with `python3 <script>.py`.

## Where the running code actually lives

This matters more than anything else here. The repo is **not** the single source of truth for the production scripts:

- **Sensor scripts run from `/home/dimitris/`, not from this repo.** These include `wind.py`, `air_quality.py`, `rainfall2.py`, `lightning_detector2.py` (via `auto_lightning.sh`), `usb_weather_logger_dual.py` (via `auto_usb_logger.sh`), `camera_capture.sh`, `download_satellite2.sh`, and `upload_WU.py`. `scripts/` holds git-tracked snapshots of them, and several have drifted from the live copies. Before editing, diff against `~/<file>` and ask which copy should change.
- **`~/air_quality_new.py` is the redesigned PMSA003I logger, waiting to replace `~/air_quality.py`.** It averages 1-s frames per minute, uses the atmospheric ("env") values in µg/m³ without the old `/10`, validates frames, and writes `air_quality_details.csv`. `--dry-run` prints the averages without writing anything. The PMSA003I is unplugged at the moment (it disturbed the I²C bus, see below). The new script stays out of service until the sensor is cleaned, because the sensor currently reads ~14× the CAMS model (PM2.5 ~93 vs ~7 µg/m³). The live script's `/10` hides that, and the true values would reach the public dashboard. Neither uploader sends PM at the moment (`SEND_PM25` in `~/upload_WU.py`).
- **Scripts that run from the repo root:** `auto_plotly.py` → `timeseries_plotly_optimised.py`, `auto_telegram.sh` → `notif_telegram.py`, plus the cron jobs below. The root copies are the live ones. The copies in `scripts/` are older snapshots.
- **Startup:** `weatherstation.service` (systemd) runs `~/run_weather_station.sh` (snapshot in `scripts/`). That script opens each long-running process in its own `gnome-terminal`, with cwd `~` for the sensor scripts and `~/weather_station` for the Plotly and Telegram scripts. It still starts `air_quality.py` at boot, although the PMSA003I is unplugged.
- **Cron** (`crontab -l`):
  - `upload_database_weather_station.py` every 30 minutes
  - `upload_awekas.py` every 5 minutes (see Readers below)
  - `plot_skewt.py` every 2 hours at :30 (for each station it stops looking once it reaches a sounding that is already plotted)
  - `get_anomaly.py` at 08:00
  - `7-day_forecast.py` at 07:00 and 19:00
  - `nowcast.py` is not scheduled at the moment (its dashboard tab is hidden too)

  Cron runs with cwd `~`, so scripts that use relative paths resolve them against the home directory. For example, the live SQLite DB is `~/weather_station.db` (about 1.9 GB), and the `weather_station.db` in the repo is a stale copy.
- `timeseries_plotly.py`, `Procfile`, and `requirements.txt` belong to an older Heroku deployment (the `heroku` git remote). They do not reflect what runs on the Pi.

## Data flow

Everything goes through one append-only CSV: `/home/dimitris/weather_station/weather_station_data.csv`.

- **Writers:** each sensor script on the Pi, plus the ESP32 boards. The boards print pre-formatted CSV lines over **USB serial** (115200 baud). `~/usb_weather_logger_dual.py` reads both boards, converts their timestamps from local time to UTC, and appends the lines. Since 2026-11-19 it runs inside `~/auto_usb_logger.sh`, which restarts it 10 s after it exits (Ctrl-C in its "ESP32 Logger" window stops the loop). It's built to survive problems (snapshots of the logger, the wrapper and the launcher are in `scripts/`):
  - A read error closes the board's port and reopens it every 10 s. Before, the error killed that board's reader thread while the process carried on with the other board; that silently lost the UV board's rows from 2026-11-17 21:36 to 2026-11-19 08:56 UTC.
  - While another program (Thonny, a diagnostic script) has a board's port open, the logger closes that port and resumes when the program closes it. So the logger no longer needs stopping for Thonny, but that board's rows aren't recorded meanwhile.
  - If a reader thread dies anyway, the logger exits so the wrapper restarts it.
  - `~/usb_weather_logger.log` records errors, reconnects, other programs on a port, non-CSV lines (except the UV board's routine `Time:` and `LOG HEALTH:` lines), and any gap of over 5 minutes in a board's rows, with how many lines arrived during it.
  - When a port is opened, the first ~64 bytes from that board often arrive corrupted (two of three starts on 2026-11-19), so a logger start or restart can lose one row per board.
  - The MCP9808 reads exactly 0.00 when the temperature board's I²C bus glitches: 12 times from 2025 to 2026-11-19, each straight after 11–28 °C, with or without the BME280 failing in the same row. Since 2026-11-19 the logger leaves such a reading out (and logs it) when the last accepted MCP9808 reading in the previous 20 minutes, or else the row's BME280 temperature, is at least 2 °C from zero (`filter_zero_glitch`). Genuine readings around 0 °C, like the many on 2026-01-01, are kept. The glitches recorded before then are still in the CSV and the DB, but the dashboard hides them (see Readers).

  The boards' USB firmware is not in this repo: copies of both boards' files (2026-09-29) are in `~/esp32_backup/`, and the current UV-board source is `~/esp32_firmware/uv_board/main.py`. Both contain the Wi-Fi password, so keep them out of git. The UV board saves its UV dark baseline to `vdark.txt` at 03:00 each night and loads it at boot, because a daylight calibration zeroes the UV index. It writes no CSV until the board's clock is set, which currently only happens when Thonny connects (in local time), so any reset silences a board. USB-serial devices must be addressed by physical port, never by `ttyUSB` number, because the numbers swap between boots (see MIGRATION.md). The older paths are legacy and no longer used: TCP port 12345 (`listen.py`) and BLE (`listen_BLE.py`). Every writer appends a **sparse row**: the timestamp plus only its own columns, with the rest left empty. Rows from different writers are interleaved and **not strictly time-ordered**, so consumers must sort and resample, never assume one row holds a full observation.
- **The temperature board's rows go missing in bursts.** It prints a row every 110.05 s whatever its sensors do (failed reads leave the fields empty). On some days, though (2026-10-08 to 10, 10-28 to 31, 11-03 to 08, 11-14, 11-18 to 19), 5 to 10 consecutive rows (9–18 min, once 26 min) went missing, up to ~30 times a day. Nearly every gap is a whole number of cycles to within a second, so the board kept running on time and the rows were lost between the board and the CSV. No other program had the port open, and the UV board on the same logger was hardly affected. The cause isn't known yet; the logger's event log should show whether the missing rows arrive corrupted (USB link: cable or the board's USB-serial chip) or not at all.
- **Light and UV:** the light column is named `Light Intensity (BH1750) (lux)`, but the UV board's sensor is now a VEML7700 (with auto-gain). On clear days it reads about 55–60 lux per W/m² of Open-Meteo's shortwave radiation, about half the usual ~110; that's consistent over time, so it's fine for trends but low in absolute terms (housing or diffuser, probably). There's no ceiling: the daily peak fell smoothly from ~34k lux in late October to ~26k in mid-November with the lower sun. The UV index is about 80% of Open-Meteo's clear-sky value on clear days.
- **I²C bus (Pi bus 1): rain gauge SEN0575 at 0x1D, PMSA003I at 0x12, AS3935 at 0x03.** On 2026-11-01 the PMSA003I turned out to disturb the whole bus: reads failed for ~0.6 s every 1.7 s (about a third of all reads, any device) even with no program reading it, and the gauge kept restarting, which wiped its tip count. So no rain was recorded from 2026-08-12 to 2026-11-01. Unplugging devices one at a time isolated it: with only the gauge connected every read succeeds and its working time counts up. The PMSA003I is unplugged and `air_quality.py` is stopped. The AS3935 was reconnected the same day and `auto_lightning.sh` restarted; with the gauge and the AS3935 on the bus, 120 of 120 reads of each succeeded. Before reconnecting the PMSA003I (after cleaning, and checking it gets 5 V), test the bus with it alone; if it still disturbs the bus, give it its own I²C bus. The gauge's working-time register (0x18, minutes since power-up) is a quick health check: it stays at 0 while the gauge keeps restarting.
- **Air temperature comes from the MCP9808.** In mid-2026 the old BME280 read several °C high with implausibly moist humidity. From 2026-10-11 it stopped answering on I²C, so the CSV has no humidity or pressure from then until 2026-11-09. A new BME280 was fitted to the same cable/connector on 2026-11-08. At first it wasn't detected either (only the MCP9808 at 0x18 answered), but it has been sending temperature, humidity and pressure since 2026-11-09 05:38 UTC. Its first readings were about 0.5 °C below the MCP9808. It dropped out while the MCP9808 kept reporting: twice briefly on 2026-11-14, and on 2026-11-17 from 04:12 to 05:51 and 20:48 to 21:38 UTC. If it disappears again, suspect the cable/connector first: check that VIN-GND is 3.3 V and test the sensor with short jumpers. The firmware only looks for the BME280 at boot, so a soft restart is needed once it's wired; a soft restart keeps the board's clock. Thonny can be used while the logger runs (see Writers above). The dashboard shows the BME280 temperature next to the MCP9808, on the Temperature tab and in the summary table (`SHOW_BME280_TEMPERATURE = True` in `timeseries_plotly_optimised.py`). The thermometer gauge and the Telegram min/max still use `Temperature (MCP9808) (°C)`. Since 2026-11-09 08:45 local, `INCLUDE_BME280 = True` in `station_now.py` adds the BME280's humidity and pressure to the AWEKAS and WU uploads (WU also gets a dew point from them). The pressure is the sensor's raw station pressure, sent as sea-level pressure without any altitude reduction. On 2026-11-09 it read 1027.8 hPa while Thessaloniki airport (LGTS) reported QNH 1028, so the two agree within the sensor's ±1 hPa.
- **Wind direction:** the vane reports only 8 positions, 45° apart. `wind.py` stores `(raw - 90 + 23) % 360`, where -90 is for the mounting and +23 (from 2026-10-31 13:35 UTC) comes from a 14-day comparison with Open-Meteo. The +23 most likely corrects the vane reporting the start of each 45° sector instead of its centre. Rows before then lack the +23. Because values now sit at 23°, 68°…, any binning must use 16 directions (as the dashboard's wind rose does), or each value lands one 8-direction bin clockwise. Average directions as vectors, never arithmetically.
- **Column names** are the header of that CSV. They are long names that include the sensor, e.g. `Temperature (BME280) (°C)`. The dashboard, the Telegram notifier, the nowcast, and the DB uploader all hard-code these strings, so renaming a column breaks every one of them.
- **Timestamps** are UTC, written as `%Y-%m-%d %H:%M:%S`. The dashboard converts them to local time for display, and it drops timestamps in the future caused by NTP glitches.
- **Readers:**
  - `timeseries_plotly_optimised.py` is the live Dash app (rewritten 2026-09-29; the previous version is `timeseries_plotly_optimised.py.bak-2026-09-29`). How it stays light on the Pi and on ngrok:
    - It parses the last ~800 KB of the CSV (24 h window) only when the file changed, under a lock (parallel callbacks otherwise got empty data).
    - Browsers poll every 30 s. A tab re-renders only when its `content_version` changes (newest reading of its columns, or image mtime), and each version is rendered once for all viewers (`_render_cache`).
    - Charts plot each sensor's own readings via `series()`, never the sparse rows directly, averaged for wind (10 min) and PM (5 min). `with_gaps()` breaks lines at outages.
    - Images are served by the `/media/<name>` Flask route, scaled to 1600 px and cached by the browser via `?v=<mtime>`. Never base64-embed them in callbacks.
    - An `after_request` hook gzips text responses.
    - `drop_zero_glitches()` hides MCP9808 and BME280 readings of exactly 0 when the sensor's last non-zero reading is at least 2 °C from zero (`ZERO_GLITCH_JUMP`). That's the same rule the USB logger applies to new rows; here it covers the glitches already in the CSV, which put a 0.0 °C spike on the chart and the thermometer gauge's daily minimum.
    - `SHOW_NOWCAST_TAB` (off) and `SHOW_BME280_TEMPERATURE` (on since 2026-11-09) toggle those views.
    - The Satellite and Cloud Camera tabs play loops through a **clientside** callback, so stepping frames costs the Pi nothing. `animation(prefix, ...)` builds a loop and `register_animation(prefix, hold)` registers its callback (`<prefix>-timer` → `<prefix>-frame`); the newest frame stays for 1 + hold ticks. Components inside tabs need `suppress_callback_exceptions=True`, which is set.
      - Satellite (`sat`): the last `SATELLITE_FRAMES` (5) frames, 800 ms each, from `/satellite-frame/<name>`.
      - Cloud Camera (`cam`): the last `CAMERA_FRAMES` (10) regular photos (not `THUNDER*`), 400 ms each, with a 2-s pause on the newest (`CAMERA_PAUSE_MS`). They're picked by file time, because the `DD-MM-YYYY_…` names don't sort by date, and photos younger than 15 s are skipped while they're still being written. They're served from `/camera-frame/<name>`, which only serves the current 10, scaled to 1600 px and cached in memory.
      - Both routes send immutable cache headers.
    - The "The Station" tab shows `assets/station_photo.jpg`. Replace that file to change the photo; its file time is part of the URL, so browsers fetch the new one.
  - `notif_telegram.py` is an async loop that sends threshold alerts to Telegram. Its rain, lightning and daily min/max checks parse only the end of the CSV (`load_data_since`): the last 512 KB (about 4 days; a day is ~130 KB), doubled until the window reaches an hour before the period needed, because rows aren't strictly in time order. That takes ~0.2 s, against ~6.5 s per call when it parsed the whole 33 MB file. Since 2026-11-19 it also sends a message when a watched measurement (`WATCHED`: MCP9808 and BME280 temperature, humidity, pressure, light, UV index) has had no reading for 30 min (`STALE_AFTER`, which skips the temperature board's routine 9–18 min losses), and another when it comes back. When all of a board's readings stop, the message points at the board, its cable and the USB logger; when only some do, at that sensor or its wiring. It checks once a minute from the last 2 MB of the CSV (about 0.6 s), not in the first 5 minutes after starting, and keeps the stopped measurements in `data_alerts_state.json` (gitignored), so restarts don't repeat alerts. The live copy is the repo-root `notif_telegram.py`, and `scripts/notif_telegram.py` matches it as of 2026-11-19. Both CSV loaders skip malformed lines (`on_bad_lines="skip"`), and each check returns early when the data failed to load, so an unreadable CSV can't crash the loop. Keep the module-level `_last_lightning_time = None`: the lightning check needs it.
  - `upload_database_weather_station.py` appends any row newer than `MAX(timestamp)` to the SQLite table `station_readings`.
  - `station_now.py` (repo root) computes the current conditions for both uploaders, from the last 2 days of the CSV: the newest MCP9808 temperature, rain since Athens midnight, 10-min wind (mean, strongest reading as the gust, vector-mean direction), UV, lux and PM2.5. Readings older than 15 min count as missing, and `current()` returns None when the station has written nothing for 15 min. Humidity and pressure come from the BME280 only while `INCLUDE_BME280 = True` (on since 2026-11-09). The rain column holds the SEN0575's running total since **UTC** midnight, written only when the bucket tips. Since 2026-11-01 `~/rainfall2.py` (rewritten) skips failed or inconsistent reads (the vendor library returned zeros on I²C errors, which made dozens of fake 0.0 rows a day), adds the gauge's count on top when the gauge restarts, and resumes the day's total from the CSV when the script restarts. Older data still drops to 0 mid-day at script restarts, so daily rain must be built from the increases (a drop or a new UTC day = restart), never by summing rows. Timestamps are parsed with `fromisoformat`, because `strptime` made each call take ~0.7 s on the Pi.
  - `upload_awekas.py` (repo root, cron every 5 min) sends those values to AWEKAS: one GET per run to `data.awekas.at/eingabe_pruefung.php` with a positional, semicolon-separated `val` (credentials `AWEKAS_USERNAME` / `AWEKAS_PASSWORD` from `.env`, the password sent as MD5; date and time in Athens local time). PM is not sent. It logs one line per run to `awekas.log`, which trims itself. `--dry-run` prints the request without sending it. AWEKAS rejects uploads less than 60 s apart.
  - `~/upload_WU.py` (its own "WU Upload" window, every 60 s) sends the same values to Weather Underground. It imports `station_now` from the repo. Its station ID and key are still hard-coded in the file. The snapshot `scripts/upload_WU.py` has those two values replaced by placeholders, so refresh it by copying the live file and replacing them again, never by copying it over unchanged. PM2.5 stays off until `SEND_PM25 = True` (WU's parameter is `AqPM2.5`; the old script sent `pm25`). Before 2026-10-31 it read the dead BME280 temperature and summed the rain column, so WU has no temperature from 2026-10-11 to 2026-10-31 and wrong daily rain before then.
  - `nowcast.py` also reads the CSV.
- Monthly CSVs are periodically split out into `raw_data_months/`.

## Secrets

The Telegram credentials (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) come from `.env` through `python-dotenv`, and `.env` is gitignored. Load new secrets the same way. `nowcast.py` and `timeseries_plotly.py` still hardcode API keys or tokens, so strip those before committing either file.

## Conventions

- Paths are mostly hard-coded absolute paths under `/home/dimitris/weather_station`. Keep new scripts consistent with that, or make them independent of cwd, because cron and the launcher use different working directories.
- Long-running scripts are kept alive by wrapper `while true` loops (`auto_*.sh`, `auto_plotly.py`), not by systemd. Some log messages in those wrappers are in Greek.
- Dashboard static files (PWA manifest, service worker, CSS, background) live in `assets/`, which Dash serves automatically.
